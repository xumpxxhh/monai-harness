# Harness Agent System Prompt 设计方法论

本文给出一套与具体产品、领域无关的 system prompt 设计方法。适用对象是带工具循环的 harness agent：模型在运行时被注入能力、环境、知识和约束，而不是只靠一段静态人设工作。

核心判断：system prompt 不是说明书全文，而是一份由 runtime 派生的、分层的、能力条件化的短契约。

---

## 1. 先定义契约，再写句子

动手写 prompt 之前，先回答六个问题。写不出来，说明契约还没定清楚。

1. **身份**：这个 agent 在什么运行环境里、对谁负责、边界停在哪里。
2. **能力**：这一刻真正能调用哪些工具，缺了哪一类工具就不能给对应指令。
3. **环境**：工作目录、时区、租户、会话身份、权限模式等可核对事实。
4. **知识**：哪些内容必须在场，哪些只给索引、按需加载。
5. **策略**：多工具之间怎么选、输出怎样才算合格。这些是 runtime 无法强制的部分。
6. **强制**：权限、校验、截断、审计由代码保证。能由代码挡住的，不要写成「请不要」。

Prompt 只补 runtime 无法强制的部分。人设可以换，骨架不能散。

---

## 2. 分层：每层只做一件事

按「谁拥有、多常变、放什么」拆层。层与层不要互相抄写。

| 层 | 拥有者 | 变化频率 | 内容 |
|---|---|---|---|
| 身份 / 默认模板 | harness | 很低 | 角色、默认工作方式、通用输出要求 |
| 能力清单 | 当前激活的工具集 | 随开关变化 | 一行存在感 + 仅对现有能力成立的选择策略 |
| 追加策略 | 用户 / 产品 | 中 | 全局偏好、组织级补充，不替换主体 |
| 场景上下文 | 工作区 / 租户 / 任务包 | 随会话变化 | 该场景的规范、禁忌、流程 |
| 知识索引 | 技能包 / 手册 / 知识库 | 随发现变化 | 名称、适用条件、完整内容位置 |
| 环境事实 | runtime | 几乎每会话都有 | 路径、时区、会话身份、当前模式 |
| 本轮覆盖 | 扩展 / 策略钩子 | 只活一轮 | 临时改写；回合结束回到 base |

三件事必须分开：

- **替换**：换掉身份主体，保留运行骨架。
- **追加**：在主体后叠加，不改身份。
- **覆盖**：只改本轮，不改 base。

用户或租户可以换人设，但不能顺手拆掉工具清单、场景上下文、知识索引和环境事实。否则每次定制都在 fork 一份 harness。

---

## 3. 推荐拼装顺序

从稳定到易变，从前缀到后缀：

```
[身份 / 默认模板，或被替换后的自定义主体]
[能力清单：当前可见工具]
[选择策略：仅对现有能力成立的 guidelines]
[产品文档 / 平台手册的索引入口（需要时才读）]
[追加策略]
[场景上下文（带来源）]
[知识索引（需要读取能力时才注入）]
[环境事实]
```

这样设计有两个原因：

- **缓存**：最少变的部分尽量靠前，避免整份前缀频繁失效。
- **调试**：人读最终字符串时，能按层定位「模型到底看见了什么」。

本轮覆盖不要就地改 base。改完能还原，并且能看出改了哪一层。

---

## 4. 能力条件化

每一条指令都必须对「此刻真实存在的能力」成立。

- 有专用搜索工具，就不要再教模型用通用执行工具去搜。
- 没有读取工具，就不要注入「去读技能文件 / 手册全文」。
- 工具没有提供清单用的一行摘要，就不要出现在能力清单里。清单是默认工作面，不是宇宙全集。
- 工具列表、选择策略、知识索引都必须从同一份 registry / loader 派生，禁止手写一份与 runtime 平行的说明书。

检验方法：关掉任意一个工具，重新生成 prompt，所有提到它的句子都应消失或改写成剩余能力下的合法策略。

---

## 5. 三种工具文本，不要揉在一起

| 文本 | 放哪 | 写什么 |
|---|---|---|
| Schema / description | 工具定义 | 参数、约束、返回值、调用方式 |
| Snippet | system prompt 的能力清单 | 一行存在感，让模型知道有这把锤子 |
| Guidelines | system prompt 的策略段 | 多工具怎么选、常见误用、何时不要用 |

不要把 schema 再抄进 system prompt。调用细节变了，prompt 一定会漂。

常驻、高频、需要被主动选中的工具，才值得占 prompt 位。偶发、懒加载、按任务临时挂上的工具，靠 description 即可。把偶发工具的策略写进 system prompt，等于每次激活都重建整份契约，并打断稳定前缀。

---

## 6. 知识用索引，领域靠外挂

Skill、SOP、手册、知识库、平台文档，默认只放四件事：

1. 它解决什么问题
2. 完整内容在哪里
3. 什么时候应该加载
4. 相对路径相对谁解析

全文用工具按需读取。默认模板保持跨领域通用；垂直领域（写代码、查日志、审合同、跑实验、做客服）通过场景上下文、技能包和激活工具集长出来。

不要把整本手册冻进每一轮前缀。知识会更新，prompt 里的副本不会。

---

## 7. 环境写成事实，不要让模型推断

工作目录、日期、时区、当前模型、会话 ID、权限模式、租户 ID，写成可核对的事实。不要让模型从人设里猜「我现在用的是哪个模型、处于哪种权限」。

事实源必须是 runtime 的真实状态。Prompt 里的环境和实际注入的环境变量、工具可见范围不一致，是一类高发故障。

---

## 8. 外源内容带来源，并设信任边界

场景上下文、租户 SOP、用户自定义主体，都是注入面。最低要求：

- 标明来源（路径、租户、配置项），让模型和调试者都知道这是工作区规则还是 harness 规则。
- 全局、祖先、当前范围的叠加顺序写死；同一逻辑范围不要加载两份相同规范。
- 项目级 / 租户级替换与扩展走信任决策。未信任前，只加载安全子集。
- 能替换主体，但不能默认获得「改权限、改审计、改工具实现」的权力。

---

## 9. 可观察，否则分层没有意义

至少能看到四样东西：

1. **最终字符串**：模型实际收到的 system prompt。
2. **各层输入**：自定义主体、激活工具、snippet、guidelines、追加文本、场景文件、技能索引。
3. **base 与本轮覆盖的差**：哪一次 turn 改过，回合结束后是否复位。
4. **派生关系**：这份 prompt 是从哪份 registry / loader 算出来的。

扩展或策略钩子对 prompt 的改写必须是链式、可复现的。Agent 行为问题里，很大一部分是「模型看到的契约和你以为的不一样」。

---

## 10. 设计流程

按这个顺序做，而不是先写一段很长的人设再四处打补丁。

### 步骤 A：划清强制与策略

列出所有「必须发生 / 绝不能发生」的事项。能用权限、schema、校验、中间件实现的，移出 prompt。留下的才进入草稿。

### 步骤 B：写最短默认主体

默认主体只保留：

- 一句话身份
- 能力清单占位
- 与领域无关的输出要求（简洁、引用资源时给出可定位标识）
- 平台文档的按需入口（若该 agent 需要解释自身）

先追求短和稳定，不追求「看起来很完整」。

### 步骤 C：为每个工具登记两类可选贡献

- 要不要出现在清单里（snippet）
- 要不要贡献选择策略（guidelines）

只在工具激活时并入。无贡献的工具可以存在，只是不占用 system prompt。

### 步骤 D：规定三套定制面

- 替换主体：换身份，不拆骨架
- 追加：叠加偏好
- 场景文件 / 技能包：长出领域

并写明发现顺序、覆盖规则、未信任时的行为。

### 步骤 E：规定本轮覆盖的生命周期

谁可以改、改的是最终字符串还是某层输入、何时复位、是否进入可观察 API。禁止「每个插件各自拼一份新宇宙」。

### 步骤 F：用能力开关做回归

对每个工具开关、每种定制面、有无读取能力、有无场景文件，生成 prompt 并断言：

- 不出现失效能力
- 不丢失骨架层
- 知识索引在缺少读取能力时不会出现
- 来源标注完整
- 稳定前缀没有被偶发工具污染

### 步骤 G：把最终字符串当产品表面来审

审的不是文采，而是：

- 模型能否在不猜测的情况下选对工具
- 新来的维护者能否指出每一段属于哪一层
- 换一个领域时，是否只换外挂、不改 harness

---

## 11. 反模式

- 把工具 schema、权限条款、整本手册、会话历史一起塞进 system prompt。
- 默认模板写死某个垂直领域的操作细则，导致其他领域只能 fork。
- 指令与当前工具集无关：教模型使用并不存在的能力。
- 用散文代替环境事实：「你通常在用户的项目里工作」。
- 外源指令不带来源，也无法区分 harness 规则和工作区规则。
- 本轮策略钩子直接改 base，或改完不复位。
- 懒加载工具为了「被看见」而写入 snippet / guidelines，导致每轮重建。
- 无法导出最终 prompt 和分层输入，出了问题只能猜。

---

## 12. 一句话标准

一份合格的 harness system prompt，应该让模型在当前这一刻清楚地知道：自己是谁、能用什么、环境是什么、缺信息时去哪里取、哪些规则已由 runtime 保证。除此之外的句子，都是候选删除项。
